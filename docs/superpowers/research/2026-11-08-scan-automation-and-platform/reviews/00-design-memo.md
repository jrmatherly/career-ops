# Design memo for adversarial review (career-ops fork, docs-only planning)

Repository: this checkout of the fork (read it; nothing here is implemented yet). Constraints that bind: AGENTS.md "Headless worker permissions" (no auto-approve flags on a new spawner; tests/headless-permission-flags.test.mjs), the one-writer rule (lib/dir-lock.mjs judges staleness by pid, every writer runs in the web pod), Data Contract (no new tracker columns; user-layer sidecars under data/), Ethical Use (evaluate only, never apply), docs/superpowers/plans/2026-11-06-reactive-resume-convergence.md Appendix B and C (publish service is internet-facing, script-free, the dashboard is never routed through it).

## Decision A. Scan-to-evaluate chain with a per-job mode

Today: web/scripts/scheduled-jobs-runner.mjs executeJob spawns scan.mjs or scan-ats-full.mjs with a temp portals overlay, records {state, rolesFound, durationMs, message} into data/scheduled-jobs.json runs[], and exits. The operator later clicks Evaluate in the dashboard, which POSTs /api/run {kind: evaluate}; web/src/app/api/run/route.ts builds the prompt (run-prompts.mjs), argv (claude-invocation.mjs claudeCliArgs, networkReadOnly scope: Read, WebFetch, WebSearch, Glob, Grep; --strict-mcp-config; --permission-mode acceptEdits with every write tool denied), spawns via spawn-cli.mjs, parses stream-json with run-cli-support.mjs parseClaudeEvent inside a ReadableStream closure, then calls the request-free web/src/lib/report-persist.mjs persistEvaluation (reserve-report-num, persist-evaluation-report, merge-tracker, release, setInboxSkip ticks the pipeline row).

Proposed:
1. Job schema gains `evaluate: { mode: "off" | "review" | "auto", rankThreshold: number (default 3.5), maxPerRun: number (default 5), cli?: string }` in web/src/lib/scheduled-jobs.ts parseScheduledJobInput. Run records gain `ranked`, `queued`, `evaluated`, `gated`, `evalErrors` counts (validateScheduledStore ignores unknown fields, so no validator change; runs[].state enum stays closed).
2. After a successful scan with mode != off the runner snapshots pending pipeline URLs before the scan (read data/pipeline.md under the pipeline lock), diffs after, so only this run's new rows are candidates (rank-pipeline.mjs ranks the first N unranked pending rows in file order, so the backlog would otherwise eat --limit). It spawns `node rank-pipeline.mjs --limit N` as a child (its main is unexported and paths are module constants; it passes no permission flag: claude -p --tools "" --disallowedTools "*"), then re-reads rank annotations for the new URLs.
3. mode review: append one row per candidate to a new user-layer ledger `data/evaluate-queue.tsv` with columns `url\tat\tjobId\trunId\trank\treason\tstate\tsource` (state queued | approved | rejected | evaluated | failed | gated; last row per url wins; append via the pipeline-lock helpers that lib/application-meta.mjs uses, appendSidecarRow and readSidecarRows, keyed by url instead of tracker num). Dashboard page /review lists queued rows, approve all / approve selected / reject; approve appends `approved` rows; the next runner tick (or a manual POST /api/review/run) evaluates approved rows in-process.
4. mode auto: evaluate candidates with rank >= rankThreshold, best first, up to maxPerRun, in the same runner process, writing the same ledger rows (state evaluated | failed | gated) so history is uniform.
5. The refactor: extract `runEvaluate({ url, cliId, root, codeRoot, today, postedAt, onEvent? }) -> { ok, num, reportFile, gate?, tokens, costUsd, error? }` into web/src/lib/evaluate-run.mjs from the route's closure (prompt, argv, spawnHeadlessCli, parseClaudeEvent, accumulateTokens, createReportEnvelopeFilter, evaluateRunOutcome, persistEvaluation). The route calls it with onEvent = send; the runner calls it without. Claude only at first (parseClaudeEvent is plain .mjs; the multi-CLI registry clis.ts is TypeScript and not importable from the runner). Gate outcomes (dealbreaker, agency_confirmation, needs_confirmation) are recorded as `gated` and never retried.
6. Runner timing: today SCAN_TIMEOUT_MS 25 min x 3 attempts bounds the runner lock stale time; evaluations take up to killMsForKind(evaluate) ~780 s each, so maxPerRun 5 adds up to 65 min; the runner lock stale time and the manual-run route's 76 min kill both move to scan budget + maxPerRun x 800 s. acquireTrackerWrite is an in-process token in the Next server, so a runner evaluate is serialized against UI runs only by merge-tracker.mjs's own acquireTrackerLock and the pipeline lock.
7. Failures: evalErrors and the first error message go on the run record through scheduled-scan-error.mjs scanFailureMessage; a rank failure (exit 1) parks the run as success-with-warning, never a failed scan.

Alternatives considered: spawning `claude -p "Run career-ops pipeline mode"` (needs Bash, Write, Playwright, so a bypass flag; refused by AGENTS.md); a JSON array like data/reply-candidates.json (whole-file rewrite, no history); new tracker columns (Data Contract forbids); a separate evaluate CronJob pod (one-writer rule).

## Decision B. Bring publish API-key minting into the dashboard

Today: publish/server.mjs mints keys only on GET /account (Pocket ID cookie session, fresh within 24 h) via auth.api.createApiKey({ body: { userId, name, permissions: { share: [upload, manage] } } }) server-side (Better Auth 1.7.14, @better-auth/api-key; /api-key/create and /update are disabledPaths over HTTP). The page is inline-styled script-free HTML under CSP default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; form-action 'self'. The key is shown once and the operator pastes it into the data root .env as PUBLISH_API_KEY; the dashboard never reads the key (web/src/app/api/shares/pull/route.ts spawns publish/share.mjs, which reads env or .env). Better Auth docs: listApiKeys and deleteApiKey require session cookies; createApiKey and updateApiKey accept a server-only userId; deleting without the owner check means mutating the DB directly.

Options:
(a) Theme the account page: copy the dashboard's token values (web/src/app/globals.css :root light vars, .dark via prefers-color-scheme) into the inline <style> of publish/pages/account.mjs. No script, no external stylesheet (CSP forbids), system font stack. Cost: one file plus a test that the page carries no <script> and no external URL.
(b) Dashboard page that lists, mints and revokes keys server-to-server: publish grows an admin route family authenticated by a new bearer credential (PUBLISH_ADMIN_TOKEN) that calls createApiKey with the allow-listed user's id and reads/deletes rows in publish.db directly (list/delete have no session-free API); the web pod calls it over the in-cluster Service and writes the minted key into /data/.env (remember-cli.mjs already edits that file). Cost: a second secret that mints share:manage keys on an internet-facing service, a NetworkPolicy change so only the web pod may reach the admin route (or an admin route bound to a second port), and the dashboard now holds the key, which the pull route's design comment says it never does.
(c) Link-out: a "Manage publish keys" link on the dashboard Shares page to `${PUBLISH_URL}/account`, which opens in a new tab; the operator signs in with Pocket ID (already signed in at the gateway for the dashboard, separate session for publish). Zero publish changes. An iframe is out: frame-ancestors 'none' and SameSite=Lax cookies.
(d) Move account management into the dashboard: Better Auth in the dashboard, rejected in Appendix B ("In-app Better Auth for the dashboard"), and the publish DB is the only state.

Proposed recommendation: (a) plus (c) now, as one small PR. (b) deferred as its own PR behind an operator decision, because it adds a minting credential to the internet-facing service for a once-a-year action. Challenge this.
