# Thread 1. Scan-to-evaluate automation with a per-job gating mode

Read-only investigation, 2026-11-08. Every claim is labelled measured (read in the code or run), inferred (follows from measured facts) or guess (no experiment settled it). File references are to this checkout.

## Overview

A scheduled scan today ends when the scanner exits. `web/scripts/scheduled-jobs-runner.mjs` records a count of new rows and nothing else, and the operator later opens the dashboard and presses Evaluate on each pending row. The pieces for a chain already exist and are separately safe. `rank-pipeline.mjs` scores pending rows with no tools granted to the agent. The web's evaluate path runs the agent with every write tool denied and the backend persists the report. What is missing is the glue, a place to park candidates for review, and a way for the runner to call the evaluate logic without a browser.

## Key concepts

**The run record.** `data/scheduled-jobs.json` holds `{jobs, runs, queue}`. A run is `{id, jobId, at, durationMs, state, attempt, message, rolesFound, engine}` (measured, `web/scripts/scheduled-jobs-runner.mjs:276`). `rolesFound` is a count parsed from the scanner's output, `New offers added: N` for the portals engine and `postingsKept` from the JSON for the full engine (measured, `extractRolesFound`). The runner never learns which URLs were new (measured). `validateScheduledStore` checks ids, states and timestamps and ignores unknown fields on jobs and runs, while `runs[].state` is a closed enum of queued, running, success, failed and cancelled (measured, `web/src/lib/scheduled-jobs-store.mjs:59-80`).

**The ranker.** `rank-pipeline.mjs` reads `data/pipeline.md`, selects `- [ ]` rows without a `rank:` segment, ranks them ten per CLI call against the first 2000 characters of `cv.md`, and appends `| rank: 4.2/5 — reason` to each row under the pipeline lock (measured, lines 55, 153, 197, 406, 484). It ranks the first N unranked rows in file order, so a backlog consumes `--limit` before this run's rows (measured). Its agent gets no tools, `claude -p --tools "" --disallowedTools "*"` (measured, line 88), so it carries no auto-approve flag and is not on the allow-list in `tests/headless-permission-flags.test.mjs` (measured, lines 43-47 list `batch-tailor.mjs`, `batch/batch-runner.sh` and `web/src/lib/cli-fencing.mjs` only). Its `main` is not exported and its paths are module constants evaluated at import (measured, lines 47 and 626), so an importer cannot call it in-process without a refactor. Exit 1 means every CLI call failed; partial failures exit 0 (measured).

**The evaluate path.** `POST /api/run {kind: "evaluate"}` in `web/src/app/api/run/route.ts` builds the prompt, builds the argv with `claudeCliArgs` from `web/src/lib/claude-invocation.mjs`, takes the in-process tracker write token, spawns the CLI through `spawnHeadlessCli`, parses the stream inside a `ReadableStream.start()` closure, runs the honesty gate `evaluateRunOutcome` and then `persistEvaluation` (measured, lines 161-636). The evaluate kind's tool scope is `networkReadOnly`, that is Read, WebFetch, WebSearch, Glob and Grep, with `--strict-mcp-config` and every write tool and Bash denied (measured, `claude-invocation.mjs` `TOOL_SCOPES`, `worker-capabilities.mjs` `KIND_CAPABILITIES.evaluate`). The agent returns the report inside a `<<report-md>>` envelope and the backend writes it, so no permission flag of the `--dangerously-skip-permissions` family is involved (measured). `persistEvaluation` in `web/src/lib/report-persist.mjs:221` is already request-free. It reserves a report number, writes the report and the tracker TSV through `persist-evaluation-report.mjs`, runs `merge-tracker.mjs`, releases the sentinel and ticks the pipeline row to `- [x]` with `setInboxSkip` (measured). The stream parser for Claude, `parseClaudeEvent`, lives in `web/src/lib/run-cli-support.mjs:246`, a plain `.mjs` module (measured). The CLI registry with `parseEvent` per CLI is `web/src/lib/clis.ts`, TypeScript, which a plain Node script cannot import (measured, 18 type-only constructs).

**Locks.** The pipeline lock (`pipeline-lock.mjs`, built on `lib/dir-lock.mjs`) serialises every writer of `data/pipeline.md`, including `scan.mjs` `appendToPipeline`, the ranker and `setInboxSkip` (measured). `merge-tracker.mjs` takes `acquireTrackerLock` on the tracker (measured, line 1298). `acquireTrackerWrite` in the Next server is an in-process token and does not reach a child process (measured, `route.ts:219`). The runner holds `withResourceLock(runnerResource)` for the whole run with a one second lock timeout, so a concurrent tick fails fast (measured, `main`).

**Thresholds.** `pipeline.triage_threshold` (default 3.5) and `pipeline.triage_min_urls` (default 5) gate the pre-evaluation `triage` mode in `modes/triage.md:111-116` (measured). `auto_pdf_score_threshold` (default 3.0) is applied after an evaluation and only decides whether a PDF is generated (measured, `modes/pipeline.md:63-65`, `batch/batch-prompt.md:604`). Neither is read by any `.mjs` or web code, and neither is the rank score (measured). They do not interact in code (inferred, they sit on different axes, a pre-evaluation filter and a post-evaluation PDF gate). A rank threshold is a third key.

## How the chain would work

The first design, a pipeline snapshot before and after the scan, a spawned ranker with `--limit`, and an evaluate function extracted from the route, failed a three-model adversarial review on four points that all three reviewers raised (see `reviews/01-design-interrogation.md`). The ranker has no URL filter and ranks the oldest unranked rows first (measured, `rank-pipeline.mjs:153-238`), a snapshot in memory is lost on a crash or a retry (measured, the runner requeues a stale claim and re-runs the scan), the route's prompt inputs live in TypeScript modules a plain Node script cannot import (measured, `web/src/lib/career-ops.ts`), and a runner-side merge is invisible to the in-process token that keeps `tracker.mjs delete` from racing `merge-tracker.mjs` (measured, `web/src/lib/core/run-registry.ts:1-24`). The design below is what survived.

1. The scan step is unchanged. The runner claims a job, scans, records the run and releases the runner lock as today.
2. If the job's evaluate mode is not `off`, the runner then computes this run's candidates from durable state. A pending row is a candidate for a job when its `data/scan-history.tsv` first-seen date is on or after the later of the job's `evaluate.enabledAt` and its previous successful run, and, in auto mode, the ledger has no row for its URL (inferred; `first_seen` is written when a URL is first added, measured at `scan.mjs:3192`, and the web already maps URLs to that date in `readScanDates`). Scan history records the board, not the job, so two jobs that run on the same day see the same new rows; the ledger queues a URL once, and the per-run cap bounds what one job's auto mode can pick up from another job's rows. A row added by hand has no scan-history row and is never a candidate.
3. It writes the candidate URLs to a temp file and spawns `node rank-pipeline.mjs --urls-file <path>`, a fork-local flag that filters the pending list before `selectBatch` (a deviation row on an upstream file, with a test). Rank keeps its tool-less argv and follows `CAREER_OPS_CLI`.
4. Mode `review` stops here. The Inbox already has the affordance the operator described, a shortlist tray that selects rows and a Score shortlist button that bulk-evaluates them through the streaming route with a cost confirmation (measured, `web/src/components/inbox/shortlist-tray.tsx:15`, `inbox-triage.tsx` `scoreShortlist`). What it lacks is the rank. `parseInbox` drops the `rank` segment and `InboxJob` has no field for it (measured), and the sort has one documented comparator (measured, `inbox-triage.tsx:169-171`). Review mode therefore adds the rank and reason to `InboxJob`, a "new from this run" grouping, and a sort by rank. No new page, no new ledger.
5. Mode `auto` appends a `queued` row per candidate to the ledger `data/evaluate-queue.tsv` with its rank and reason, including rows that came back unranked (reason `unranked`, never evaluated on their own). A separate drain step, on every tick and under its own lock, takes `queued` rows whose rank is at or above the threshold, best first, up to the per-run cap and the daily cap. Before each one it checks that the pipeline row is still pending and the tracker has no row for the URL, writes a `running` row with the run id, and then evaluates.
6. The evaluation reuses the route itself. The drain POSTs to `http://127.0.0.1:3000/api/run` with `Host: localhost` and consumes the NDJSON stream to its result event. The origin guard admits a loopback host with no browser headers, which the scan tick already relies on (measured, `web/src/lib/origin-guard.mjs` `checkRequest`, home-cluster HelmRelease `Host: localhost`). The evaluation runs inside the Next process, takes `acquireTrackerWrite`, keeps the `networkReadOnly` fencing and `--strict-mcp-config`, and persists through `persistEvaluation`, which also ticks the pipeline row. The route is not extracted; it gains one kind (below). The extraction stays as the fallback in the plan's Appendix B.
7. The drain writes `evaluated`, `failed` or `gated` with the message. Gate stops (dealbreaker, agency confirmation, needs confirmation) are never retried (measured gate kinds, `web/src/lib/evaluation-gate.mjs:7`). `failed` retries at most twice with a cooldown. A rate-limit or usage-limit error stops the batch and leaves the rest `queued`.
8. The run record gains `ranked`, `queued`, `evaluated`, `gated` and `evalErrors` counts and the first error text, chosen by `scanFailureMessage` in `web/src/lib/scheduled-scan-error.mjs`.

Auto mode and untrusted postings. In the dashboard a human chooses which posting gets an agent that holds `cv.md` and can fetch any URL. Auto mode would hand that agent to every posting that passes the title filter (inferred, raised by all three reviewers). The plan therefore limits auto mode to postings whose ATS is in `JD_TEXT_API_ATS` (measured, `liveness-api.mjs`), fetches the JD text first with `fetchJdViaKnownApi` from `browser-extract.mjs` (measured, line 1072), and evaluates it under a new `evaluate-text` kind with the `localReadOnly` scope, which has no network tool and so no exfiltration channel (measured, `worker-capabilities.mjs` `CAPS.localReadOnly`). Postings with no API text are marked `skipped` with reason `no-api-text` and left to the Inbox, so the drain does not refetch them every tick. Auto-mode reports carry no web research, since `modes/_shared.md` and `modes/oferta.md` ask for WebSearch in comp and legitimacy checks (measured, five uses); the report header says so, and whether that trade is right is an open question below. The `webSearchOnly` scope exists (measured, `worker-capabilities.mjs:55`) but reopens a query channel to the web. The residual risk is an agent that can read the pod's files, including `/proc/self/environ`, and write them into a report that a later networked agent might read. The plan gates auto mode on a check of that path and denies `Read` on `/proc/**` and the data root `.env` in the kind's argv.

## The auto-mode ledger in the data layer

The Data Contract forbids new tracker columns and the convergence program chose append-only TSV sidecars keyed by tracker number for application detail (measured, `lib/application-meta.mjs`, `lib/application-events.mjs`, trail row 2026-11-07T01:06:10Z). A queued posting has no tracker row yet, so its key is the normalised posting URL from `url-key.mjs`. The existing sidecar reader rejects a first cell that is not a positive integer (measured, `lib/application-meta.mjs:57-73`), and the web never imports root modules but reads sidecars through a core CLI dump (measured, `DATA_CONTRACT.md:66`), so the ledger gets its own root module and the web reads it the same way. Only `appendSidecarRow` and the pipeline lock are reused. Any new `data/` file is already a user-layer path (measured, `USER_PATHS` contains `data/`), and the file gets a row in `DATA_CONTRACT.md`.

File `data/evaluate-queue.tsv`, columns `url`, `at`, `jobId`, `runId`, `rank`, `reason`, `state`, `source`. States are `queued`, `running`, `evaluated`, `failed`, `gated` and `skipped`. Last row per URL wins. A `running` row older than the evaluate kill timer plus a margin is read as `failed`. Values pass through `tsvCell`, because the reason is model text derived from an untrusted title (measured, `lib/application-meta.mjs:22`).

## Where rank reaches the dashboard

`parseInbox` in `web/src/lib/pipeline-table.mjs:31` recognises the `rank` label so it does not corrupt columns, then drops it. `InboxJob` in `web/src/lib/career-ops.ts:104` has no rank field (measured). The dashboard cannot show or sort by rank today, which the review page needs.

## Timing and budget

`SCAN_TIMEOUT_MS` is 25 minutes and `MAX_ATTEMPTS` is 3 (measured). The lock's staleness is judged by whether the owner pid is alive, so a longer run does not need a longer stale time (measured, `lib/dir-lock.mjs:262-285`). An evaluation is killed at 740 seconds (measured, `killMsForKind` in `run-cli-support.mjs:443`). The drain is a separate step with its own lock so a scan never waits behind evaluations, and the manual run route keeps returning when the scan finishes (inferred). The route's own `maxDuration` of 800 seconds bounds each loopback evaluation (measured, `route.ts:33`).

## Token cost at today's volume

Measured on the Mac data root, no personal data copied. Six transcripts of 2026-11-05 in the data root's Claude projects folder, each carrying the report envelope and the `oferta.md` mode (measured, marker counts per file), so all six are dashboard evaluations, under the default model had a median of 38 turns, 70 thousand output tokens, 2.7 million cache-read tokens, 620 thousand cache-write tokens and about one thousand uncached input tokens each (measured, token sums per transcript). The daily tracked-boards job added 66 rows on its first run and then 3, 2 and 1 rows on the next three days (measured, `data/scan-runs.tsv`). The weekly full sweep has not run yet, so its volume is unknown. A rank batch is one CLI call per ten rows with a prompt of company, title, URL and a 2000 character CV excerpt (measured), which is small next to one evaluation.

Inferred cost at today's rates. Auto mode on the daily job would evaluate one to three rows a day, about 3.4 million tokens each counting cache reads, under a subscription's weekly cap rather than per-token billing. The first run of a new job is the risk, 66 candidates at once, which is why the per-run cap and the review mode exist. The full sweep's first run is a guess until it runs once with mode `off`.

## Failures

`scanFailureMessage` picks the last `Error:` or `Fatal:` stderr line, or the spawn error for a timeout (measured). A rank child that exits 1 should leave the scan a success with a warning, not a failed run, because the rows are already in the pipeline (inferred). An evaluation failure is per row and goes on the ledger as `failed` with the message, and the run record carries the count (inferred).

## Alternatives considered

- Spawning `claude -p "Run career-ops pipeline mode"`. The pipeline mode needs Bash, Write and a browser, so the worker would need a bypass flag, which AGENTS.md forbids for a new spawner and `tests/headless-permission-flags.test.mjs` fails (measured).
- A JSON array like `data/reply-candidates.json`. Simpler to write, no history, and a crash mid-rewrite loses the queue (inferred).
- New tracker columns. Forbidden by the Data Contract and the convergence decision (measured).
- A separate evaluate CronJob pod. The lock judges staleness by pid and the second pid namespace reads a live lock as stale (measured, Appendix B of the convergence plan).
- Importing `rank-pipeline.mjs`. Its `main` is unexported and paths are module constants, so spawning it as a child is the smallest change and keeps its tool-less argv as the only permission surface (measured).

## Recommendation

Keep the scan step as it is. Add a `--urls-file` filter to the ranker. Serve review mode through the Inbox, which already shortlists and bulk-evaluates, by surfacing the rank. Give auto mode a durable ledger in the user layer, a drain step that evaluates through the existing route over loopback, a per-run cap and a daily cap, and an ATS-text-only rule with a no-network scope. Default every job to `off`. Run the first weekly full sweep with evaluation `off` to learn its volume before turning on `review`.

## Open questions for the operator

- Should `auto` mode also generate PDFs above `auto_pdf_score_threshold`, or stay report-only? The evaluate kind never renders a PDF (measured), so PDFs would be a second run per row.
- Which CLI should scheduled evaluations use when the job does not say? The pod image sets `CAREER_OPS_CLI=claude` (measured, `deploy/Dockerfile`).
- Is a backlog of unranked older rows acceptable to leave unranked, or should the first review-mode run rank the whole pending list once?
- The brief asked for a review queue page with approve all, approve selected and hand-picked rows. The Inbox shortlist already does that for pending rows; is a separate page still wanted once the Inbox shows rank and groups rows by run?
- Should auto mode stay limited to postings whose ATS exposes JD text through an API (the safer default), or evaluate every ranked row with the network scope the dashboard uses?
- Auto-mode reports lose the WebSearch-based comp and legitimacy research the dashboard's reports have. Accept that and label it, or allow `webSearchOnly` and accept the query channel?
- On a Mac install the runner is started by cron or launchd and the dashboard may be off. The plan leaves rows `queued` with reason `dashboard-offline` in that case. Is auto mode wanted on the Mac at all?
