# Thread 2. Routing Claude Code through CLIProxyAPI

Read-only investigation, 2026-11-08. Claims are labelled measured, inferred or guess. Cluster facts come from the home-cluster repository's templates and its rule file `.claude/rules/apps/cliproxyapi.md`; nothing on the cluster was touched and no key was read.

## What runs on the cluster

CLIProxyAPI is `eceasy/cli-proxy-api` v8.0.58, the Docker image the upstream project `router-for-me/CLIProxyAPI` documents in its quick start (measured, HelmRelease template and help.router-for.me quick start). It runs in namespace `llms` as Service `cliproxyapi` on port 8317, so the in-cluster URL is `http://cliproxyapi.llms.svc.cluster.local:8317` (measured, the two consoles use exactly that URL). An HTTPRoute exposes it on the internal gateway at `llms.<domain>` (measured). Its NetworkPolicy admits ingress on 8317 from the `network` namespace and from the two console pods in its own namespace only (measured, `networkpolicy.yaml.j2`). A career-ops pod in namespace `career-ops` is not admitted today (measured). Reaching it needs either a new `from` entry for the career-ops web pod or the gateway hostname, which the pod can reach only if cluster DNS resolves it and hairpins through the gateway (inferred, not tested).

The proxy pools three Claude Max logins added through its manager console and stored as token files on its volume (measured, rule file). Routing is weighted round-robin with one hour session affinity, rebinding on quota errors, three request retries and model-level cooling so a Fable 429 cools only Fable on that login (measured, seed config keys). The `claude-seat-pacer` plugin paces new conversations across the three seats toward each seat's weekly plan (measured, rule file). So the three subscriptions pool, with per-session stickiness, rather than rotate on a schedule (inferred from those settings).

Clients authenticate with one client key from `access.api-keys` sent as `Authorization: Bearer` (measured, rule file and the quick-start page). More client keys can be added only in the manager console, which persists to the volume copy of the config, not to Git (measured). The API surface is Anthropic Messages, OpenAI chat completions and Gemini (measured, the rule file records `/v1/models` listing 19 Claude models and a Haiku request answered on both `/v1/messages` and `/v1/chat/completions`). Whether it serves `/v1/messages/count_tokens` is unknown (guess, not documented in either repository).

## Probe from the Mac, no key

`GET https://llms.<domain>/healthz` answered 200 with JSON. `GET /v1/models` answered 401 with `{"error":"Missing API key"}`. `GET /v1/messages` answered 404, consistent with a POST-only route (measured, 2026-11-08). The hostname resolves through the internal gateway address. So the proxy is reachable from the operator's network and bearer-gated. An authenticated model list and a Claude Code session through it are unproven here; the rule file records both as measured by the operator on 2026-11-07.

## What Claude Code does with a gateway, from the docs

Authentication precedence runs in this order. Cloud provider variables, then `ANTHROPIC_AUTH_TOKEN` sent as `Authorization: Bearer`, then `ANTHROPIC_API_KEY` sent as `x-api-key`, then `apiKeyHelper`, then `CLAUDE_CODE_OAUTH_TOKEN`, then profile credentials, then the `/login` subscription (measured, https://code.claude.com/docs/en/authentication, "Authentication precedence"). In non-interactive `-p` mode an environment credential is used without a prompt (measured, same page). `ANTHROPIC_BASE_URL` alone keeps the subscription login as the active credential, and a gateway that forwards such traffic to Anthropic must forward the OAuth capability in `anthropic-beta` (measured, https://code.claude.com/docs/en/llm-gateway). While a gateway credential is active the request carries that credential instead of the subscription login, and billing lands on whoever owns the credential the gateway forwards (measured, same page). CLIProxyAPI forwards its own pooled OAuth tokens, so usage lands on the three subscriptions (inferred). The gateway protocol page says Claude Code posts to `/v1/messages?beta=true` and treats token-counting endpoints as optional (measured, https://code.claude.com/docs/en/llm-gateway-protocol). The upstream CLIProxyAPI guide for Claude Code sets exactly `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` in `settings.json` and suggests `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` (measured, help.router-for.me/agent-client/claude-code.html). The same page also sets `bypassPermissions`, which this fork must not copy (measured, AGENTS.md).

So the pod needs `ANTHROPIC_BASE_URL=http://cliproxyapi.llms.svc.cluster.local:8317` and `ANTHROPIC_AUTH_TOKEN=<client key>`, and must drop `CLAUDE_CODE_OAUTH_TOKEN`, because the bearer token outranks it and keeping both only invites the doctor warning and confusion (inferred from the precedence list). Whether Claude Code 2.1.319, the version pinned in `deploy/Dockerfile:12`, behaves exactly as the current docs describe is a guess until a scratch pod runs one `claude -p` through the proxy.

## What in the fork notices or breaks

- Nothing in the fork reads `ANTHROPIC_BASE_URL` (measured, repository grep). The web spawns `claude` with the whole `process.env` and no `--model` (measured, `web/src/lib/claude-invocation.mjs:152-168`, `web/src/app/api/run/route.ts:213`), so the pod env alone controls routing.
- `doctor.mjs` `checkBillingSource` warns on any `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` with the text that the session bills per token even on Pro or Max (measured, lines 179-219). Behind this proxy the text is wrong, because the proxy spends subscription quota. The warning is printed only by the human `doctor.mjs` run. `ANTHROPIC_API_KEY=x node doctor.mjs --json` returns warnings without it, so the web's doctor route never shows it (measured, 2026-11-08). A proxy-aware exception is one branch, when `ANTHROPIC_BASE_URL` is set and is not `api.anthropic.com`, say "routes through a gateway at <host>; billing follows the gateway's credential" with no fix lines, pinned in `tests/doctor-billing-source.test.mjs` (inferred).
- `batch/batch-runner.sh` maps `spend_tier` to the literal ids `claude-haiku-5-5`, `claude-sonnet-5-5` and `claude-opus-5-5` (measured, lines 699-705). The proxy must serve those ids or alias them; the rule file records 19 Claude models listed, which covers them (inferred). Its rate-limit detection is a case-insensitive regex over the worker log for `rate limit`, `too many requests`, `429`, `quota exceeded`, `try again later` and `temporarily unavailable`, and a session-limit regex that pauses the batch (measured, lines 1033-1038). A proxy that exhausts every seat and returns an Anthropic-shaped 429 is caught. A proxy that returns a generic 500 or a connection reset falls through to a failed offer (inferred). The proxy's own three retries run before Claude Code sees anything (measured config).
- `--strict-mcp-config` is unaffected; it concerns MCP servers, not the API endpoint (measured, `claude-invocation.mjs:163`).
- The web's fatal stderr regexes kill a run on `unauthorized`, `forbidden` or `invalid api key` (measured, `web/src/lib/run-cli-support.mjs:65-82`), so a wrong client key fails fast with a readable message (inferred).
- The dashboard's cost figure is `total_cost_usd` from the CLI's result event, priced by the CLI at list price whatever the proxy spends (measured, `run-cli-support.mjs:277`). The usage meter sums local transcripts and frames them as subscription windows (measured, `web/src/lib/claude-usage-scan.mjs`). Behind a pool of three seats those windows describe no single account (inferred).
- `lib/llm-outbound.mjs` does not list a proxy host, but `openai-eval.mjs` and `openrouter-runner.mjs` call `assertLlmRequestAllowed` without `requireLlmHost`, so the host check does not run and only the body inspection applies (measured, lines 246-255, `openai-eval.mjs:399`).

## The other evaluators as proxy targets

- `openai-eval.mjs` and `openai-tailor.mjs` honour `OPENAI_BASE_URL`, `OPENAI_API_KEY` and `OPENAI_MODEL`, speak chat completions with a Bearer header, and refuse a non-loopback `http` base URL (measured, `openai-eval.mjs:146-148, 225, 249`). So they can target the proxy's `/v1/chat/completions` over `https://llms.<domain>` with a Claude model id, but not the plain `http` in-cluster Service URL without a code change to the loopback rule (inferred). They are not wired into the web or the scheduled runner (measured).
- `openrouter-runner.mjs` hardcodes `https://openrouter.ai/api/v1/chat/completions` (measured, line 84). Not a proxy target without a new base-URL variable.
- `gemini-eval.mjs` uses the Google SDK with `GEMINI_API_KEY` and no base URL override (measured). Not a proxy target.
- Cost tables in `utils/token-tracker.mjs` list Claude 3.x rates only (measured), so any dollar figure from those scripts is stale regardless of the proxy.

## How the env would reach the pod

A `[career_ops]` field in `cluster.toml` renders into `template/config/kubernetes/apps/career-ops/career-ops/app/secret.sops.yaml.j2` as a `stringData` key wrapped in `#% if career_ops.<field> %#`, and the Secret is injected whole with `envFrom`, so each key becomes a pod env var; Reloader restarts the pod on a Secret change (measured, commit dd52dd2 and the templates). `publish_api_key` touched nine files: `validate.py` `CareerOps`, `cluster.schema.json`, `cluster.sample.toml`, the two `.j2` templates, `test_validate.py`, the valid fixture, and the app rule (measured). The proxy needs two fields, a non-secret `anthropic_base_url` rendered into the HelmRelease env and a secret `anthropic_auth_token` rendered into the Secret, both optional and conditional, plus a rule that the token is set only when the URL is, and `claude_oauth_token` left empty when the proxy is used (inferred). `CLAUDE_CODE_OAUTH_TOKEN` is rendered unconditionally today, as an empty string when the field is blank (measured). Claude Code does not read an empty variable as a credential (guess; verify on the scratch pod). The NetworkPolicy of the proxy needs a `from` entry for the career-ops web pod, gated on `career_ops_enabled` and `cliproxyapi_enabled` (inferred). A validator rule that `anthropic_base_url` requires `[cliproxyapi]` is optional; the URL could point anywhere Anthropic-compatible.

## Alternatives considered

- Keep the single OAuth token. Works today; one seat, one weekly cap, and rotation is a `cluster.toml` edit (measured, Appendix C of the convergence plan).
- `ANTHROPIC_API_KEY` instead of `ANTHROPIC_AUTH_TOKEN`. Claude Code would send `x-api-key`, and the proxy is documented for Bearer only (measured, rule file). Unproven whether it accepts `x-api-key`.
- `apiKeyHelper` in a settings file. Adds a file to the image for a static key; the env variable is simpler and the image has no settings file today (measured, `deploy/README.md`).
- Routing the OpenAI-shaped evaluators instead of Claude Code. They are not wired into the web or scheduled runs, so they would not serve thread 1 (measured).

## Recommendation

Route the web pod's Claude Code through the proxy with `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN`, add the NetworkPolicy entry, add the proxy-aware branch to `checkBillingSource`, and prove it on a scratch pod before the real pod changes, with one `claude -p` with a trivial prompt through the proxy, the proxy's usage page showing the request, and `doctor.mjs` printing the gateway line. Leave `batch-runner.sh` and the OpenAI-shaped evaluators unchanged until a run shows a need. Give career-ops its own client key only if the operator wants per-client usage in the console, since a second key lives on the proxy's volume and is lost on a re-seed (measured, rule file).
