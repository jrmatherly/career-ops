## 3. CV surfaces

Three separate things, with different data models.

a) /cv (app/cv/page.tsx -> components/cv-editor.tsx). A raw markdown textarea for `cv.md` with ReactMarkdown + remark-gfm preview, autosave 600 ms (cv-editor.tsx:26), sessionStorage draft key `career-ops.cv-draft` (:25). Writes via POST /api/cv with `expected:{content,exists}` compare-and-swap and optional backup (app/api/cv/route.ts:29-55, lib/cv-write.mjs, lib/cv-editor-state.mjs reducer). PDF upload/ingest: components/cv/cv-ingest.tsx + /api/cv/ingest. There is no structured model; cv.md is free markdown. Core parses it with lib/cv-markdown (core) and web/src/lib/cv-studio/base-cv.mjs:22 `parseBaseCv(md, cvMarkdown)`.

b) CV Studio (/pipeline/[id]/cv-studio -> components/cv-studio/cv-studio.tsx 18K, section-card.tsx 17K, coverage-meter, cv-preview). It edits an already generated tailored HTML file in `output/`, not a payload:
   - Server: `loadStudio(n)` (lib/cv-studio/server.ts:84) finds the tailored HTML via the pdf-index manifest, `parseBlocks(html)` into a tree of sections/items/bullets by the template's class names (lib/cv-studio/html-blocks.mjs:108), builds a `StudioDoc` (lib/cv-studio/studio.mjs:91, aligning tailored bullets with cv.md bullets by word similarity and JD keywords from core `keyword-match`), and loads saved edits from `.career-ops-web/cv-studio/<report>.json` (server.ts:76, 129-139). Unsupported layouts return `unreadable-layout`.
   - Edits model `StudioEdits` v1 = {preset{length,tone}, use per bullet (tailored|base|custom), hidden[], shown[], order{}, restored{}} bound to `sourceHash` of the HTML; stale hash clears edits (studio.mjs typedef, `parseEdits`:150). Reducer `studioReducer` (:206), undo stack 30 (:411).
   - Preview: entirely client-side. `html = useMemo(() => renderBlocks(tree, resolved.view, {added}))` (cv-studio.tsx:100) is fed to `CvPreview` (cv-preview.tsx), an iframe `srcDoc={previewHtml(html)}` with `sandbox="allow-same-origin"`, scaled to 816 px width, measured on load; `page-estimate.mjs` (PREVIEW_PAGE_PX 1056 = Letter at 96 dpi, `contentHeightPx`, `frameHeightPx`, `previewPageCount`) gives a heuristic page count. `previewHtml` (lib/cv-studio/preview-html.mjs:58) injects a fit stylesheet and converts `**bold**` and `_italic_` to tags in text nodes only. No server round trip per edit, no cache needed.
   - Save: PUT autosaves edits after 500 ms (cv-studio.tsx:187) via createPutOrder race handling (lib/cv-studio/put-order.mjs). POST op "save" -> `renderEditedPdf` (server.ts:193) writes `<name>-edited.html` and runs generate-pdf.mjs (fact gate included), then `markTrackerReady`. POST op "keywords" returns keyword hits for custom text.
   - AI: POST /api/cv-studio/[n]/rewrite (maxDuration 150, rewrite/route.ts:9) -> `runRewrite` (lib/cv-studio/rewrite-run.ts:16) -> headless CLI, with `unsupportedRewriteClaims` using core verify-cv-facts + cv-voice (server.ts:165).

c) How preview/tailored HTML is produced today: the web does not call build-cv-html.mjs. `grep build-cv-html` in web/src hits only a comment (lib/cv-studio/html-blocks.mjs:8). The /api/run `pdf` kind sends an agent a prompt (lib/run-prompts.mjs:244-247) telling it to read modes/pdf.md, cv.md, profile, report and the resolved template, and emit the full HTML in a `<<cv-html format="...">>` envelope (lib/cv-envelope.mjs:31-32, parser :83, streaming filter :186). The backend persists the HTML, runs generate-pdf.mjs, marks the tracker. So HTML is LLM-authored per run, minutes long; Studio only post-edits it.

d) What a payload-driven live preview could reuse. build-cv-html.mjs (repo root, 1150 lines) is a deterministic renderer: `node build-cv-html.mjs <input.json> <output.html> [template.html]`, or `--preview <input.json>` writing output/cv-preview.html, or `--markdown`. It reads a JSON payload with keys lang, page_format, country, candidate, sections, summary, competencies, experience, projects, education, certifications, awards, interests, skills, consent (the builder prints this list as warnings when unknown keys are passed; ENTRY_FIELD_SPECS in lib/cv-payload-schema.mjs:20-60 gives per-section required/known fields, e.g. experience {company, role, location, context, dates|period, bullets}). I measured it: tiny payload against an empty CAREER_OPS_ROOT, 0.085 s wall including Node startup (my run, scratch dir; output valid:true, with warnings for my wrong top-level keys). Templates: templates/cv-template*.html (default, compact, executive, jake, leadership, modern, zh-minimal) resolved by cv-templates.mjs (`resolve cv`); core module also wrapped in web at lib/core/cv-template.mjs. There is no cache, no server wrapper, and no web route for it. Cost model: file in, file out per call; a web route would need to write the payload to a temp file under `.career-ops-web/`, spawn (about 100 ms), and return the HTML. The builder imports generate-pdf.mjs and path-resolver.mjs at load (build-cv-html.mjs:~40), so it reads DATA_ROOT at import and it is per-process, which suits per-request spawn. Inference: debounced (300 to 500 ms) spawn per edit is feasible, or port nothing and import the module with `import(pathToFileURL(rootScript("build-cv-html")))` as server.ts:24 does for keyword-match, if it exports a render function (I did not check exports beyond the CLI; `grep ^export` returned none, so the CLI is the only entry; verify before planning an in-process call).
   - Core also has `verify-cv-facts.mjs`, `verify-cv-structure.mjs`, `cv-title-check.mjs`, `jd-skill-gap.mjs`, `keyword-match.mjs`, `ats-payload.mjs` and `verify-ats.mjs`: these are the natural backends for a Check panel; web already wraps keyword-match (/api/keyword-match) and verify-cv-facts (server.ts:167).

e) /api/cv-pdf (app/api/cv-pdf/route.ts): GET only, serves an existing PDF inline, resolved by `n` (report number, via data/pdf-index.tsv), `application` (tracker row via its report cell), or company slug fallback; never renders. Page count in the Studio is the heuristic above; real page count comes from generate-pdf.

## 4. Auth and multi-tenancy

- There is no auth. `grep -i "cookies(|set-cookie|password|bearer"` in web/src finds only incidental hits (config-form.tsx, posting-url.mjs, apply/diagnose.ts, employer-source.mjs, cv/pdf-text.mjs). `src/app/login/` contains only `loading.tsx` (a skeleton for a sign-in page) with no page.tsx: a dead, unreachable route directory. No session, cookie, token, or password env var.
- The only gate is src/proxy.ts: same-origin (Sec-Fetch-Site/Origin) plus loopback Host filter (lib/origin-guard.mjs) over everything except `_next/static|_next/image|favicon.ico` (proxy.ts:45). Opt-ins: CAREER_OPS_WEB_ALLOWED_HOSTS (also drives the bind in server.mjs / lib/bind-host.mjs) and CAREER_OPS_ALLOWED_ORIGINS. Design intent in origin-guard.mjs header: the bind is the access control. Any public share page would be blocked by this guard (non-loopback Host returns 403) unless the matcher excludes it (e.g. `/s/` routes) and the server binds beyond loopback; those two changes weaken the model for the whole app, so a separate process or deployment is cleaner. Inference.
- Single data root assumption: `careerOpsRoot()` has 103 call sites across 49 files in web/src (my count of `careerOpsRoot()`), all process-global and env-derived, no per-request tenant parameter. Plus cwd-derived `path.resolve(process.cwd(), "..")` (career-ops.ts:195 `codeRoot`) and `resolveCodeRoot(process.cwd(), process.env)` everywhere scripts are spawned (core-cli.ts:37, ~25 route sites). Core scripts also resolve their own root by env (`path-resolver.mjs`), so multi-tenancy needs a per-request env passed into every spawn (runCoreCli already builds `env`, core-cli.ts:39) or one process per tenant.
- `.career-ops-web/` state dir under the data root: apply-prefill.log (app/api/apply/prefill/route.ts:37), logo-cache (api/logo/route.ts), runs (api/runs/save/route.ts:39), pdf-tmp (lib/pdf-paths.mjs:88), chats (lib/assistant-chat-store.mjs:12), cv-studio edits (lib/cv-studio/server.ts:77), legacy memory.md (lib/profile-memory.mjs:75). Also run registry in-memory (lib/core/run-registry.ts) and file locks in lib/core/dir-lock.mjs (48.9K) keyed to the data root.

## 5. Headless worker boundary

- lib/claude-invocation.mjs:30 `WRITE_CAPABLE_TOOLS = [Write, Edit, MultiEdit, NotebookEdit, Bash]`; NETWORK_TOOLS = [WebFetch, WebSearch] (:37); `Task` always denied (:40). `scopeFrom(allowed)` (:78) derives a deny list as everything write-capable not in the allow list. Three scopes (:108): persisting (Read,WebFetch,WebSearch,Write,Edit,Bash,Glob,Grep), networkReadOnly (Read,WebFetch,WebSearch,Glob,Grep), localReadOnly (Read,Glob,Grep). `toolScopeFor(kind)` (:126) maps through `capabilitiesFor(kind)` in lib/worker-capabilities.mjs: pdf = localReadOnly (no Bash since #2172, "must never regain it"), research/evaluate/cover = networkReadOnly, fix-portal = workspaceWrite, unknown kinds = localReadOnly (worker-capabilities.mjs:~95-115). `KNOWN_KINDS` = pdf, research, evaluate, fix-portal, cover (:71). `verifyClaudeArgs` (claude-invocation.mjs:212) checks the shipped argv.
- Rule to follow for any new AI feature: the agent returns text (envelope or JSON), the backend validates and persists, and the agent gets read-only scope. The Studio rewrite is the template: `REWRITE_SCOPE = scopeFrom("Read")` (lib/cv-studio/rewrite-run.ts:11), `CAPS.localReadOnly`, `fencingReport` gate -> `rewriteGate` (refuses a runtime with no verified fencing, reason "unfenced"), `spawnHeadlessCli(...)`, 120 s kill; reply parsed in lib/cv-studio/rewrite.mjs (`buildRewritePrompt`, `parseRewrite`, `MAX_INSTRUCTION`) and checked by core `verifyFacts/auditClaims` (server.ts:165-185) so invented claims are flagged. "Improve this bullet" is essentially that route today.
- /api/assistant (app/api/assistant/route.ts, maxDuration 120): chat advisor. Spawns the chosen CLI headless with `ADVISOR_SCOPE = scopeFrom("Read,WebFetch,Glob,Grep")` (:16) and `CAPS.networkReadOnly`, a system preamble (lib/assistant-preamble.mjs, memory + file pointers) and trimmed history (assistant-history.mjs). It cannot write; a status change proposed by the assistant is confirmed by the user in the UI (components/assistant-status-confirmation.tsx) and written client-side through `writeAssistantStatus` -> /api/status. Chats persist in `.career-ops-web/chats/<id>.json` (/api/assistant/chats).
